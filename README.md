# Мониторинг рабочей активности — лист Proteus

Лист показывает активность команды: разбивку на подчинённые подразделения,
KPI по категориям активности и динамику за несколько месяцев.

## Файлы

| Файл | Что это |
|---|---|
| `activity.sql` | **1.0, в работе.** Единственный запрос листа. 27 колонок, гранулярность: подразделение × месяц. |
| `activity.chart.js` | **1.0, в работе.** Единственный график листа: KPI-полоса, стек состава, две линии динамики, таблица. |
| `activity.v2.sql` | **2.0, кандидат.** Точные гранулярности: три вида строк в одной выдаче. |
| `activity.v2.chart.js` | **2.0, кандидат.** Недельные спарклайны рядом с долями в таблице, поиск, база «по всем», режим долей. |
| `DESIGN_SYSTEM.md` | Дизайн-система TeamPulse. Токены, компоненты, правила визуализации. |

Версии независимы: у 2.0 своё пространство имён (`wa2`), файлы 1.0 не тронуты.
Переключение на 2.0 — замена запроса и скрипта в графике Proteus, откат — обратная замена.

Раньше файлов было четыре: три графика (`kpi`, `barchart`, `table`) и общий запрос.
Все три строились на одной витрине `prod_proteus.monitoring_work_activity_kavtorin`,
делили пространство имён `mr` в `window.__pvtState` и не могли обмениваться состоянием —
поэтому объединены в один график.

## Контракт Proteus — менять нельзя

`activity.chart.js` написан под ограничения хоста и повторяет структуру прежних файлов:

* ECharts — только холст. Вся визуализация — HTML/CSS/SVG в overlay поверх него.
* Хост — **последний** элемент с атрибутом `_echarts_instance_`; его `<canvas>` прячется,
  overlay добавляется через `appendChild`.
* В самом конце файла глобально присваивается пустой `option` со `scatter`.
* ES5: без backticks, стрелочных функций, `let`/`const`.
* Поиск узлов — только `overlay.querySelector`, без `document.getElementById`.
* Семь блоков в фиксированном порядке, без перенумерации:
  `CFG` → вход и хелперы → трансформация → форматирование → разметка → монтаж → `option`.

## Поток данных

```
витрина ──► activity.sql ──► data[] ──► buildModel() ──► aggregate(подразделение)
             только суммы      строка      индекс по         KPI + ряды графиков
             и счётчики        =           подразделениям    под выбранный срез
                               подразд.
                               × месяц
```

**В SQL нет ни одного деления и ни одной оконной функции.** Запрос отдаёт только
аддитивные величины, поэтому JS пересчитывает весь лист под любое подразделение
на клиенте — клик по строке таблицы не ходит в базу.

Правило отбора колонок: в выдаче остаётся поле, которое нельзя получить
из соседних. Итог по категории не отдаётся — полосы «1–2 недели» и «больше
2 недель» непересекающиеся и покрывают категорию целиком, поэтому итог
складывает JS.

Что переехало из SQL в JS:

| Было в SQL | Стало |
|---|---|
| `CASE … AS category_little_group` (категория строкой) | четыре колонки `cnt_month_*`, пивот в JS |
| `CASE … AS color_col` (цвета в запросе) | палитра в `CFG.colors` / `CFG.cats` |
| `duration_active`, `avg_duration_active`, `calls`, `avg_calls` — ≈120 строк оконных функций | числитель и знаменатель отдельными суммами, деление и выбор базы дней в `ratioAct()` / `ratioTalk()` |
| `prev_*` как готовая дельта | сырой счётчик прошлой недели, вычитание в `aggregate()` |
| `low`, `high`, `leave`, `weekend` — итоги категорий | сумма двух полос, `SUM_KEYS` в `aggregate()` |
| доли `% от активной численности` | `tableRow()` |
| итог «все подразделения» | `aggregate(null)` |

Формула средних теперь одна и та же для месяца и для периода — меняется только
область суммирования. Раньше «за месяц» и «в среднем» считались разными формулами.

Из прежней трёхуровневой coalesce-цепочки средней активности остались два уровня:
плановые дни, а если их в срезе нет вовсе — все дни. Средний уровень (будни без
плана) срабатывал только там, где в подразделении нет ни одного планового дня;
если такое в витрине встречается, верните в запрос пару `dur_wd_sum` / `dur_wd_cnt`
и промежуточную ветку в `ratioAct()`.

## Интерактив

| Действие | Что меняется |
|---|---|
| Клик по строке таблицы | KPI-полоса и оба графика пересчитываются под это подразделение; появляется чип фильтра. Повторный клик или строка «Все подразделения» — сброс. |
| Клик по столбцу состава или по точке линии | Месяц отмечается: значение в шапке правых панелей переключается на него. |
| Клик по легенде | Категория убирается из стека и из шкалы. Последнюю выключить нельзя. |
| Клик по шапке колонки | Сортировка таблицы, повторный клик меняет направление. |
| `Enter` / `Space` | То же, что клик, для строк, легенды, столбцов и шапок. |
| `Escape` | Снимает фильтр подразделения и отметку месяца. |

Подсказка на строке таблицы содержит разбивку по метрикам и подсказывает,
что строка кликабельна.

## Карта полей

`CFG.fields` задаёт только два измерения — `lvl_down_nm` и `date_structure`.
Остальные колонки читаются по именам из трёх списков в БЛОКЕ 3:

* `WEEK_KEYS` (11 полей) — снимок последней закрытой недели (`flag_last_week = 1`)
  и предыдущей (`= 2`). Складываются по месяцам внутри подразделения.
* `PERIOD_KEYS` (4 поля) — прогулы и работа в выходные, считаются за весь период.
  По месяцам не аддитивны, поэтому берётся максимум по месяцам подразделения.
* `MONTH_KEYS` (10 полей) — состав по категориям месяца и компоненты средних.
  Чистые суммы.
* `SUM_KEYS` — итоги, которых в запросе нет: `low`, `high`, `leave`, `weekend`
  собираются сложением своих полос.

Переименовали колонку в запросе — поправьте соответствующий список.

## Допущения

1. **Сотрудник относится ровно к одному `lvl_down_nm`.** Иначе итог «все подразделения»
   (сумма по строкам) завысится.
2. **Недельные и месячные признаки сведены к месяцу.** `cat_week` — недельный признак,
   `cat_month` — месячный; в одной плоской выдаче общий ключ только один. Если последняя
   закрытая неделя попадает на стык месяцев, её строки лягут в два месяца и сотрудник
   посчитается дважды. Точное решение — завести в витрине `week_dt` и вынести недельный
   снимок в отдельный запрос. Прежний запрос таблицы вёл себя так же.
3. **Прогулы и работа в выходные** — периодовые счётчики; максимум по месяцам даёт точное
   значение, когда сотрудник присутствует в витрине во всех своих месяцах.

## Отличия от прежних трёх графиков

Функциональные:

* Один запрос и один график вместо трёх; состояние общее, поэтому фильтр по
  подразделению действует на KPI и на графики.
* Правые панели динамики — линии вместо баров (динамика одной метрики читается линией).
* Таблица сортируется по любой колонке; первой строкой идёт итог «Все подразделения»,
  он же кнопка сброса фильтра.
* Активная численность вынесена в отдельную колонку — по ней можно сортировать.

Оформление — по `DESIGN_SYSTEM.md`:

* Одна палитра категорий на весь лист. Раньше «недоработка» была `#d4a5b5` в стеке
  и `#d97b70` в таблице — один смысл красился двумя цветами.
* Из светофора убран жёлтый (§3.1): цветные заливки шапок и ячеек таблицы заменены
  нейтральной шапкой с тонкой цветной чертой под заголовком блока.
* В дельтах убраны стрелки `▲▼` (§4.7): направление несёт знак, оценку — цвет.
  База сравнения названа один раз в подзаголовке листа, а не в каждой пилюле.
* Кегли, отступы и радиусы — только из шкал §2. Панели и KPI-карточки получили
  одинаковое оформление: тень без рамки, радиус `--r4`.
* Числа по §7: тонкий пробел в разрядах, запятая в дробной части, типографский минус,
  `п.п.` у процентных изменений, моноширинные цифры в колонках.
* Подсказки — один конструктор и один делегированный обработчик (§5).
* «Прогулы» и «Работа в выходные» помечены как «не сравнивается» вместо пустоты (§4.8):
  метрика периодовая, сравнивать с прошлой неделей нечего.
* Изменение доли звонков в Talk не окрашено (§4.7, правило 2): больше не значит лучше.
* Ось значений всегда от нуля, оси Y нет, значения подписаны у точек и столбцов (§6.1–6.2).
* Доступность: строки, легенда и столбцы доступны с клавиатуры, есть `:focus-visible`,
  `Escape` и `prefers-reduced-motion`.

## Версия 2.0

Что добавлено и зачем. Всё проверено на моках в Chromium так же, как 1.0.

### Точные гранулярности (`activity.v2.sql`)

Главная слабость 1.0 — недельный снимок сводился к месяцу: на стыке месяцев
сотрудник последней недели попадал в два месяца, а прогулы приходилось брать
максимумом по месяцам. В 2.0 выдача из трёх видов строк с одним набором колонок:

| `row_kind` | Гранулярность | Что несёт |
|---|---|---|
| `month` | подразделение × месяц | состав по категориям, компоненты средних |
| `week` | подразделение × неделя | численность и категории недели — только для спарклайнов |
| `snapshot` | подразделение | снимок последней недели, прогулы, работа в выходные |

Цена — три плоских `GROUP BY` вместо одного (`UNION ALL`), по-прежнему без
оконных функций и делений. Если диалект поддерживает `GROUPING SETS`, сводится
к одному проходу; JS различает виды строк и по `row_kind`, и по пустому
`date_structure`, так что скрипт с таким запросом тот же.

Неделя в ветке `week` — `dateTrunc('week', calendar_dt)`, понедельник. Если
в витрине есть своя колонка недели с той же разметкой, что у `cat_week`,
подставьте её. `flag_last_week` в этих строках говорит скрипту, какая неделя
последняя закрытая: всё, что позже, в спарклайн не попадает.

**Совместимость назад:** если строк `snapshot` в выдаче нет, `activity.v2.chart.js`
считает недельные поля по правилам 1.0. Проверено: на выдаче 1.0 обе версии
графика показывают одни и те же числа.

### Таблица: тренд без клика

* **Спарклайн рядом с «Долей»** в блоках «Недоработка» и «Переработка».
  Число — недельная доля от активной численности, ровно та же, что в 1.0,
  с той же сортировкой. Линия в цвете категории — те же недельные доли
  за последние 12 закрытых недель (`CFG.sparkWeeks`), её последняя точка
  совпадает с числом. Тренд живёт в блоке своей категории, а не в отдельной
  колонке. Нет строк `week` в выдаче — остаётся одно число, как в 1.0.
  Шкала от нуля до максимума строки (§6.1).

  **Недоработку и переработку не складываем** — это разные сигналы с разной
  логикой реагирования: недоработка — красный флаг, действовать сразу;
  переработка в зависимости от задач бывает нормой, следить надо за её
  длительностью. Сумма прятала бы, какая категория растёт.
* **Поиск по названию** появляется, когда команд больше одной страницы.
  Перерисовываются только строки и пагинация — фокус остаётся в поле,
  `Escape` очищает запрос. Итог «Все подразделения» виден всегда.

### База сравнения «по всем» (§11.1)

При выбранном подразделении карточки показывают рядом с долей долю по всем
подразделениям («21% активной численности · по всем 12%»), правые панели —
значение по всем за тот же месяц. Временное погружение в команду базу не меняет —
видно, лучше команда остальных или хуже. Без окраски: это относительная доля
без утверждённой цели.

### Стек состава: люди или доли

Переключатель «Люди / Доли» в шапке панели (§4.9). В режиме долей каждый месяц
приведён к 100%, доли подписаны внутри сегментов белым halo — читаются на любой
заливке. Подсказка в обоих режимах показывает и людей, и долю.

### Идеи, которые в 2.0 не вошли

* **Несколько команд разом** (Ctrl+клик по строкам). Агрегация это умеет —
  `aggregate()` складывает любой список, — но объединённый срез не даёт
  сравнить команды между собой, только посмотреть их сумму. Ценность спорная.
* **Линия «по всем» на графиках динамики** при фильтре. Полезно, но третья линия
  (значение, среднее, все) в панели высотой 110px уже шумит. Пока база «по всем»
  дана числом в подписи.
* **Состояние в ссылке** (§11.7): внутри Proteus адресная строка не наша.
* **Δ к прошлой неделе для Talk в таблице**: колонка `prev_talk_20_30` в выдаче
  есть, в таблице места под ещё один столбец нет. Есть в KPI-карточке.
